# QA 포트폴리오 — 이영준

> 모바일 수집형 RPG **트릭컬 리바이브**의 실행 기록과, PC 게임 2종의 테스트 설계로 구성했습니다.
> 테스트 케이스 총 **1,189건**, 버그 리포트 16건, 배포 전 체크리스트 24항목, 검증 보고서 2편(PDF).

플랫폼과 장르가 달라지면 무엇을 봐야 하는지가 달라집니다. 그 차이를 드러내려고 모바일과 PC, 실행과 설계를 나누어 담았습니다.

넥슨 협력사에서 라이브 게임 모니터링과 패치 지원을 하며 얻은 감각과, 대상 타이틀을 2023년 10월부터 약 3년간 플레이해온 유저 관점을 함께 반영했습니다.

## Section A — 패치 대응 테스트 케이스 (1,115건)

특정 버전 패치를 기준으로, 대분류·중분류·소분류 체계의 실무형 대량 테스트 양식으로 만들었습니다. 콘텐츠 영역별로 문서를 나눈 이유는 패치마다 건드리는 곳이 달라서, 그때그때 실행할 범위만 골라 쓸 수 있게 하기 위해서입니다.

드림랜드 27건 중 26건(N/T 25건 · N/A 1건)은 기간 한정 콘텐츠라 진입할 수 없어 미실행으로 처리했습니다. 검증 항목 자체는 설계해두고, 실행 가능한 시점에 돌릴 대상으로 남겨두었습니다.

## Section B — ISTQB 양식 테스트 케이스 (39건)

같은 대상 중 한 콘텐츠를 골라 표준 양식으로 다시 썼습니다.

```
TC_ID · 테스트 대상 · 목적 · 사전 조건 · 절차 · 예상결과 · 실제결과 · 결과
```

양식을 둘로 나눈 건, 현장에서 빠르게 돌리는 문서와 근거로 남기는 문서가 서로 다르다고 봤기 때문입니다. Section A는 앞쪽, Section B는 뒤쪽입니다.

**결과** — PASS 34 / FAIL 3 / BLOCK 1 / SKIP 1 (통과율 87.2%)

PASS 34건은 실제 플레이로 확인한 결과이고, FAIL 3건·BLOCK 1건·SKIP 1건은 결함 처리 흐름과 결과 상태 구분을 보여 주려고 만든 **가상 결과**입니다. 선행 TC가 실패하면 후속 TC를 BLOCK으로 처리하고, 체크리스트 NG 항목과 버그 ID로 연결했습니다. 예를 들어 TT-010(가상 FAIL)이 실패하면 TT-011이 BLOCK으로 이어지고, 해당 항목은 체크리스트 NG와 버그 리포트까지 같은 ID로 추적됩니다.

## Section C · D — PC 게임 테스트 설계 (35건)

모바일만으로는 검증 축이 한쪽에 치우친다고 판단해, 오래 플레이한 PC 게임 두 종을 대상으로 테스트 설계를 추가했습니다.

| | Section C — MMORPG | Section D — AOS |
|---|---|---|
| 대상 | 장비 강화·증폭 (19건) | 아이템 제작 (16건) |
| 초점 | **데이터가 제대로 남는가** | **실시간으로 제대로 도는가** |
| 고유 축 | 재화 정합성, 강화 수치 상한, 인벤토리 한계 | 전투 중·이동 중·사망 상태의 기능 제약 |
| 결과 | PASS 15 / FAIL 3 / BLOCK 1 | PASS 15 / FAIL 1 |

양쪽 모두 해상도 변경, 창모드 전환, Alt+Tab, 키 바인딩처럼 **모바일에는 없는 PC 고유 검증 축**을 넣었습니다.

> 두 자료는 실제 플레이 경험을 바탕으로 구성한 **가상 시나리오**입니다.
> 결괏값은 검증 흐름을 보여주기 위한 설계상 가정이며, 실제 서비스의 결함 보고가 아닙니다.

Section D에 BLOCK을 두지 않은 것도 판단입니다. FAIL(ER-011)에 의존하는 후속 TC가 없어, 억지로 연결하는 대신 각각 독립 TC로 두었습니다.

→ [PC 게임 테스트 설계 상세](section-c-d-pc-tc/PC_TC.md)

## Section E — 전투/밸런스 테스트 설계 (25건 + 체크리스트 13항목)

에피드게임즈 [트릭컬 리바이브] QA담당자 공고의 담당 업무인 **전투/밸런스 QA**와 **국내/글로벌 라이브 이슈 대응**에 맞춰 새로 설계했습니다. 위 1,189건과는 따로 집계합니다.

| 영역 | 무엇을 보는가 |
|---|---|
| 성격 시너지 (7건) | 발동 경계(1·2·3·4명), 시너지 2종 동시 발동 시 적용 방식, 아군 전원에게 적용되는지 |
| SP·스킬 (6건) | 저학년 발동·SP 초기화, 기절과 시전 캔슬, 고학년 재사용 시간 경계·감소 중첩 하한 |
| 피해 계산 (5건) | 성격 상성 배율, 물리 면역, %피해 감소 합계 100% 경계, 표시 피해량과 실제 HP 감소 |
| 버프·전투 환경·랭킹 (5건) | 중첩 불가 버프, 무적 종료 직후, 배속·자동 동일성, 백그라운드·네트워크 복귀, 랭킹 기록 정합성 |
| 밸런스 모니터링 (2건) | 패치 전후 동일 덱 클리어 시간, 상위권 채용률 급변 사도 추적 |

> 실제 빌드에서 실행한 기록이 아닌 **테스트 설계 샘플**입니다. 시너지 적용 규칙은 인게임에서 확인했고, 단계별 수치는 공개 커뮤니티 자료 기준 참고값입니다.

설계 가운데 5건(BT-015 · 016 · 018 · 019 · 020)은 같은 계열의 판정을 딜리버리(보스전 체험 콘텐츠)에서 직접 확인한 실측 기록과 연결했습니다. 예를 들어 BT-020(무적 중 피해 방지)은 셀리네 무적 중 피격에서 SP 회복 트리거가 발동하지 않는 것(EXP-02)으로, BT-019(중첩 불가 효과 재적용)는 다야 쓰라림이 출처가 다르면 서로 덮어쓰지 않고 따로 쌓이는 것(EXP-03)으로 대비해 볼 수 있습니다.

라이브 이슈 대응 체크리스트는 인지 → 재현 → 판단 → 전파 → 조치 → 사후 순서로 13항목을 두고, 항목마다 라이브 모니터링 실무에서 같은 판단을 해 온 지점을 적었습니다.

→ [전투/밸런스 TC 및 라이브 이슈 체크리스트](section-e-combat-balance/전투밸런스_TC.md)

## 버그 리포트 (16건)

| 출처 | 건수 | ID |
|---|---:|---|
| 라이브 이슈 | 1건 | `BUG-LIVE` |
| 공식 오류 게시판 유저 제보 | 3건 | `BUG-BRD` |
| 콘텐츠 내 이슈 | 9건 | `BUG-CLT` |
| 배포 전 검증 | 3건 | `BUG-EVT` |

각 리포트에 심각도, 우선순위, 재현율, 재현 환경, 재현 절차를 넣었습니다. 심각도와 우선순위를 따로 적은 건 둘이 다른 이야기이기 때문입니다. 표기 오타처럼 영향은 작아도 먼저 고쳐야 하는 게 있습니다.

출처별로 ID를 나눠 관리하고, 체크리스트의 NG 항목과 같은 ID로 이어집니다.

> 라이브 이슈·유저 제보·콘텐츠 버그 13건은 공식 공지와 공식 라운지 오류 게시판에 올라온 **실제 이슈와 유저 제보를 정리한 것**입니다.
> 배포 전 검증 3건(`BUG-EVT`)은 방법론을 적용해보려고 **직접 만든 가상 시나리오**입니다.

## 배포 전 체크리스트 (24항목)

배포 전에 확인할 항목과 판정 기준을 정리하고, 가상 시나리오로 결과까지 남겨 본 문서입니다. 실제 빌드에도 같은 양식과 판정 기준을 그대로 쓸 수 있게 만들었습니다.

NG가 나오면 해당 TC ID와 BUG ID를 같이 적었습니다. 나중에 이 항목이 왜 걸렸는지, 어느 리포트로 넘어갔는지 되짚을 수 있어야 한다고 생각했습니다.

```
요구사항 → 체크리스트 항목 → 테스트 케이스 → 버그 리포트
```

무언가 바뀌었을 때 어디를 다시 봐야 하는지 찾아 들어가기 위한 구조입니다.

**결과** — OK 20 / NG 3 / 보류 1 (통과율 83.3%)

NG 3건은 각각 `BUG-EVT-001` ~ `BUG-EVT-003`으로 이어지며, 수정 대기 상태로 남겨두었습니다.

## 제안서

검증 산출물과 별개로, 특정 콘텐츠를 QA 관점에서 분석하고 개선을 제안하는 문서도 작성해봤습니다.

QA가 결함을 찾는 데서 멈추지 않고 "무엇을 어떻게 개선하면 좋을지"를 다른 조직이 검토할 수 있는 형태로 정리하는 일도 필요하다고 생각했습니다. 리포트와는 성격이 다른 문서라 따로 두었습니다.
